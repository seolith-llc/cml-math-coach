## Response summary

**Root cause (a real bug, not a missed fix).** Both features were deployed (13:26Z) before her test (18:20Z). Her device had installed the app before Cloudflare Access went on (Nov 11 ~01:50Z).
- Its service worker serves the cached app offline.
- When it checks for an update, `/sw.js` now gets Access's sign-in redirect, and browsers reject redirects for service-worker scripts, so the update silently fails.
- So the device stays on the old version forever, and never shows the sign-in page. Neither of her emails mentions signing in.
- The same will happen to every device when its 30-day sign-in expires.

**Fix**
1. **Access bypass for the service-worker scripts only:** a new "Math Coach app updates" app (`/sw.js`, `/push-sw.js`, `/workbox-*`; generic code, no data, already public in the repo). Pages and APIs stay behind sign-in. The script verifies that `/sw.js` loads without sign-in while `/index.html` still needs it.
2. **`public/push-sw.js`:** when a new version installs, it checks sign-in (`/?auth-check=1`, redirect: manual). If signed out, it deletes the caches and unregisters, so the next open goes to the sign-in page. This unsticks old copies.
3. **`src/pwa.ts`** (replaces the bare registerSW):
   - checks for updates on open, on foreground and hourly, so long-open tabs update;
   - checks sign-in (at most every 10 minutes); if expired, unregisters, clears caches and reloads to the sign-in page, at most once a minute so it can never loop.
   - `tests/pwa.test.ts` covers it.

**On her point 1:** the Parent dashboard row is on Home, one tap from anywhere via ⌂. It is deliberately not on the practice page, so a child mid-round isn't sent to the parent area.

**Verification**
- `npm run check`: 752 tests.
- Chromium simulation: the app installs and caches; then the auth check gets a 302; the app reloads exactly once and the guard prevents loops; no errors.
